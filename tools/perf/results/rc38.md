# Solar on Floptle 0.117.0-rc38 — trial before 0.117.0 stable (2026-10-26/27, 22:36–00:10)

Solar HEAD 7253c0c (already pinned to rc38), run from a clean `git worktree` of it
so the other agents' uncommitted edits stay out of the numbers. Every run was
silent (ALSA null), on XWayland with vsync Off, one engine at a time under the
shared lock. `load` is `uptime`'s 1-minute average before the run. Five other
agents queued on the lock all night, so the load ran 2–17; the comparison that
counts is the second set (rc33 → rc38 → rc37 back to back, load 2–10).

## Verdict

| item | result |
|---|---|
| 1. bench, rc37 vs rc38 (and rc33) | **PASS**: rc38 matches rc33 within the spread (dig p95 15–16 ms, rover p95 21–22 ms, 0–2 frames over 33 ms) |
| 2. export ships `.floptle/textures.ron` (0550) | **PASS**: shipped byte for byte, nothing copied by hand; the build's pictures are smoother than the same build without it |
| 3. Sea at density 0 (0551) | **PASS, applied**: the density warnings go (3 → 0 a run); water.at, the underwater look, swimming and Solar's floating unchanged |
| 4. 0549 guards, 0552 handles, Solar's workarounds | **PASS**: 0 through-frames; a retired handle reads valid=false, name=nil, never reaches the slot's new node; staleprobe and wheelprobe PASS |
| 5. compute prototype (rain rings) | **Works, kept OFF**: +0.6 ms GPU at Medium, +0.02 ms CPU; it can only be drawn as a decal, and the base's ground did not take decals. Six API notes below |

**Recommendation: promote rc38 to stable.** It fixes everything it set out to (moving-world physics back to rc33, exported textures, density-0 water, handles that name one node for life) with no regression in Solar's benches, probes or smoke tests. The compute API works as documented; its rough edges (below) are for 0.117.x/0.118, not blockers.

## 5. Compute — the first use: rain rings on the GPU (prototype, off)

`scripts/rain_fx.lua` param `computeRipples` (default **false**) and
`shaders/rainRipples.wgsl`: a 512² wave height field over a 16 m patch round the
camera. `emit` (one invocation per 0.5 m lattice cell: the drops landing this
step), `step` (the wave equation, ping-ponged between two f32 buffers) 60 times a
second, `shade` once a frame into a `gpu.texture` drawn as a decal. Probe:
`rain.sh … RAIN_ONLY=compute` (rainprobe part `compute`), heavy rain at the base.

| | Medium | High |
|---|---|---|
| GPU total, rings on / off | 8.74 / 8.12 ms (3 pairs) | 14.18 / 13.75 ms (2 pairs) |
| compute passes | shade 0.35–0.38, emit 0.19–0.21, step 0.07 | shade 0.22–0.26, emit 0.12–0.15, step 0.06 |
| rain_fx CPU | 0.080 / 0.061 ms | 0.077 / – |

The first version found each drop per height cell (3×3 lattice cells a texel):
`compute step` alone was 1.3–1.7 ms. One invocation per drop instead: 0.07 ms.

**Why it stays off:** the texture reads back right (`gtex:read`: 199k of 262k
texels lit) and a solid-magenta test draws on the runway slab, but neither it
nor a plain `scorch.png` decal (control) drew on the ground at the base, where
`terrain.query` 1.7 m over the drawn ground reads −7.7 (inside rock) and a ray
down from 3.7 m misses. Rings on the pad only are not worth 0.6 ms. The right
home is the existing rainFx screen pass sampling the field — which a screen
shader cannot do yet (note 1).

### Compute API notes for E (card-ready)

1. **A screen shader can't sample a compute texture.** `stage post` passes take
   no texture slots (ScreenShader has only `params`; post-processing.md "Not
   yet"), so `gpu:N` cannot feed a full-screen effect, the cheapest place to draw
   a simulated field over everything the camera sees (wet ground, rings, snow
   cover, heat haze). Ask: texture slots on screen shaders, settable with
   `setShaderTexture("pass.slot", ref)` like their params.
2. **A decal laid the frame its `gpu.texture` is made never draws.** The decal
   page is built before the frame's compute requests register `gpu:N`;
   `ensure_texture` misses, the console says "the picture gpu:1 will not load",
   the page is dropped and the warning is never repeated, so the mark stays
   invisible. Repro: `local t = gpu.texture{w=64,h=64}; decals.add{texture=t.name,
   pos=…, normal=…, size=4}` in one update. Workaround: wait two frames. Fix:
   register gpu textures when `gpu.texture` is called, or let a page whose
   picture is missing retry (`decals.rs` `rebuild_decal_page`, `compute_jobs.rs`).
3. **Every helper in the file is compiled against each run's params.** A run
   that doesn't pass `cell` fails if *any* helper reads `params.cell`, even one
   its entry never calls: "shaders/rainRipples.wgsl:31: invalid field accessor
   `cell`" from the `clear` run. The guide says a run binds only what its entry
   uses; params should follow the same rule (drop uncalled functions, or declare
   every param any entry uses).
4. **Each `compute.run` is its own submission, with a new uniform buffer and
   bind group** (`compute.rs` `run_queued`). The fixed cost shows in the timer:
   `emit` (1,024 invocations, almost no work) reads 0.19–0.21 ms while `step`
   (262,144 invocations) reads 0.07 ms. Batch the frame's runs into one encoder
   (timestamp queries per pass), and reuse uniform buffers.
5. **`floptle check` doesn't look at compute at all**: a `.wgsl` with a syntax
   error and a script running `compute.run("shaders/missing.wgsl", …)` both pass
   with 0 errors. Compile every `.wgsl` against an empty prelude (or each
   `compute.run` literal's binds) as it does `.flsl`.
6. Params are f32 only. Integers (`n`, cell counts) go through `u32(params.n)`,
   and a matrix or a vec3 is 9 or 3 names. A `vec2/3/4` and `u32` param would make
   world-space work (view-projection, a patch's axes) far less fiddly.

The rest worked as documented: `gpu.limits()` (128 MB buffers, 8 storage buffers,
256 invocations), WGSL errors at the file's own line, `gpu.free` on Stop, `:read`
a frame later, entry points named `step` and `clear`.
