# Long sessions, launch hitches and the Graphics tab (2026-11-02, engines .1374 → .1377)

Machine: RTX 4060 (256 MiB BAR1), Solar on a 7200 rpm disk, XWayland, vsync off. The box is
shared with other agents, so the load is quoted next to every run. Raw logs are in
`/mnt/disks/3tb/.floptle-shared/solar/work/perfgfx/` (soakB, soakA, rocketB, rocketA, gfx, smoke).

## 1. What grows in a long session (tools/perf/soakprobe.sh)

The soak loop runs one cycle of about 70 s, over and over. A cycle:
- puts the crew down on new ground (a bearing that turns 137° each cycle, 250–570 m out);
- walks 14 s and digs 6 laser bites;
- opens the inventory, the ops board and the map;
- steps time warp up to the top and holds it for 8 s;
- does a crew switch (`]` `[`);
- launches the starter rocket from the VAB, burns 10 s, then reverts to the builder.

Every 30 s it logs a `SOAK` line: frame p50, p95, max and mean; per-script ms; Lua KB; nodes; craft; engine counts; terrain memory; and each script's global-state size via getfenv.

The soak is cut into 275 s segments, each its own locked play. Segment 0 makes a save in slot 14 and later segments CONTINUE it. One segment does about four cycles, which is roughly 15–20 minutes of what a player does.

**Measured growth (before the fixes, engine .1376, 2 segments, 18 windows):**

| | first window | last | |
|---|---|---|---|
| frame p50 | 17.2 ms | 16.3–19.5 ms | flat within the noise; load 2.8–13 |
| Lua memory | 24 MB | 18–48 MB | sawtooth from the GC; no upward trend |
| nodes | 817 | 1,071 | +250, all of it from the craft below |
| live craft | 0 | 3 | see below |
| terrain memory | 622 MB | 602–761 MB | levels off (2.7 GB after a long top-speed warp in the trial run) |
| vessel_controller | 0.16 ms | 0.69 ms | rises with the craft count |
| crew_strip + flight_hud + dock_row + iva + crew_alerts_hud | ≈0.3 ms | ≈1.1 ms | all scale with the craft count |

**Per-craft cost.** Every craft left in the world adds about 0.15–0.25 ms a frame across the scripts. The main contributors:
- vessel_controller, including dockTick's `findScripts` for every pair;
- crew_strip, flight_hud, dock_row and crew_alerts_hud, which call `findScripts("vessel_controller")` every frame;
- flight_ops `fleetSync`, which deep-copies and re-saves the whole fleet once a second.

Nothing removes spent stages, wrecks or craft you walked away from: they are saved in `fleet.craft` and rebuilt on every scene load. A menu round-trip doesn't clear them either, so an hour of launching without reverts keeps getting slower.

This matches the static audit: in segment 1 the probe's reverts failed and three craft piled up, and vessel_controller and the HUD scripts rose with them.

**Before and after the fixes.** Both runs had 2 segments of 18 windows (each segment about 4 cycles). The before run used the working tree without this pass, on .1376. The after run used this pass plus the patches: segment 0 on .1376, segment 1 on .1377, a wheel-physics-only change.

| | before | after |
|---|---|---|
| frame p50, mean of windows | 19.6 ms | 18.5 ms |
| frame p95, mean of windows | 33.3 ms | 27.2 ms |
| worst frame per 30 s window, median | 203 ms | 82 ms |
| windows with a frame over 200 ms | 9 of 18 | 5 of 18 |
| flora_field ms/frame | 0.60 | 0.41 |
| flora_field slope within a segment | +0.085 ms / 5 min | +0.036 ms / 5 min |

Load was 2.8–13 for the before run and 6–10 for the after run. objectives rises by about 0.2 ms over the first segment in both runs and stays flat after that: that is state (an accepted contract), not growth.

**Growth in script state, with a fix:**
- flora_field `cuts` and mineral_field `breaks` keep one list per species (or rock kind) for every patch ever built. `regrow()` walked every list 7 (flora) and 5 (rocks) times a second, allocating a table and running a string match for each one. That cost grows with the ground walked. Fixed in `fields_perf.patch`.

**Growth checked and found bounded:** decals (capped), particles, props, Lua memory, script globals (only `system_generator.GENSPEC` grows, by one record per star system the warp visits), event listeners and timers, crew portrait cameras.

**Possible bug seen by the probe:** on a CONTINUE'd save (segment 1, booted the way the menu's CONTINUE loads a slot), `vessel_spawner.revertToBuilder()` answers "nothing to revert" right after an in-VAB launch. On a fresh save the same call works.

## 2. Launch and load hitches (perfbench `rocket`, script sampler on)

| | before (.1375, load 20/9) | after (.1375, load 2.4/3.5) |
|---|---|---|
| first frame of the system scene | 871 ms: graphics 79 ms of scripts, plus shader compiles | 502 ms: shader and pipeline compiles (graphics 68 + settings 55: the one-off migration from the settings slot to the file, on a fresh install) |
| far_bodies cache write at the reveal | **505 ms** (`far_bodies:cache_write:492`) | none |
| launch scene load, worst frame | 361 ms: graphics **111 ms** | 201 ms (asset decode); graphics 0 |
| launch_load scripts/frame | far_bodies 4.28, flora 2.06, graphics 1.05 | flora 1.27, far_bodies 0.92, graphics 0 |
| c_ascent | p95 27.6, max 951 (untimed), >33 ms: 51 | p95 27.0, max 210, >33 ms: 26 |
| c_throttle_change | max 410 (far_bodies 68 ms in the 94 ms frame) | max 37, 0 frames over 50 ms |

**Causes:**
- **`save.slot()` switches.** `graphics.lua` and `settings.lua` both read the player's settings by switching to the "settings" save slot. Each switch waits for the game's slot to be fsynced and then re-reads it whole. That cost 70–220 ms on every scene load and launch, charged to graphics, settings and missions, with no line accounting for it. Fixed: the store is now `user://settings.json`.
- **`far_bodies` cache writes.** `assets.writeBytes` fsyncs on the frame: 70–920 ms on this disk. Fixed: writes are held until `onDestroy`, which runs under the loading curtain (`far_bodies_perf.patch`).
- **The flora_field spike in the ascent** (22.7 ms in one frame): `clear_base` → `scatter.near` over the base's 215 m makes one Lua vec3 per hit (`vec3:new` 12.5 ms). This is engine card G. The patch caches `base_layout`'s seven `save.get` calls once a frame (they ran once per judged prop) and the rare-plant record that `rare_tick` copied every frame.
- **missions:** prog_tick read `system.home`, `rare.<home>` and `world.<home>` once per milestone each second. They are now read once per tick (`home_niches`). The 10 ms frames were mostly the lazy slot reload after a slot switch, landing on missions' first `save.get`.
